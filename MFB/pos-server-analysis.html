Infrastructure review

The cash register is doing a server's job.

ESB POS slows to a crawl every night between 01:00 and 03:00. This document works through what is actually causing it, and compares three ways forward.

Site: Miss Fish System: ESB POS Hours: 18:00 – 06:00 Status: Quotation in hand
01

Summary

The machine acting as the ESB server is a 15-inch all-in-one cash register. At around five tablets it still ran normally. It now serves fifteen devices while also running the main cashier lane.

Diagnosis
Under-specified host
A 15 W mobile processor carrying a four-role workload.
Network
Ruled out
Gigabit LAN, Ruijie switch, Wi-Fi on standby only.
Recommendation
Split the roles
Dedicated business desktop as server; keep the Iware as a till.
Why this is not just “buy a faster PC” Moving the server off the cashier lane fixes two problems at once: it frees the capacity that Chrome POS is currently eating, and it removes the single point of failure that can stop every section at once.

03

Root cause

Four factors stack on top of each other, and they all peak at the same hour.

1 — Three times the load it last handled well

At around five tablets this machine behaved normally. Fifteen devices now depend on it. Before midnight the restaurant is quiet and everything still works; from 01:00 every terminal is live at once.

2 — A laptop processor in a sealed chassis

The i5-10310U is a 15 W mobile part built for thin laptops. Inside an all-in-one till with a small fan, sustained load pushes it into thermal throttling — clock speed drops exactly when demand is highest.

3 — The server is also the busiest cashier

A local Chrome POS window competes for the same cores and memory that fifteen other terminals depend on. This is the load that a dedicated server would remove entirely.

4 — Memory pressure lands on a SATA drive

Once 16 GB fills, Windows pages to disk — and that disk is SATA, confirmed. Every page-out adds latency to database writes, which slows posting further, which holds memory longer. The platform has no NVMe path, so this cannot be fixed on the current unit.

Still unmeasured No Task Manager capture has been taken during peak. Screenshots of CPU, memory and disk between 01:00 and 03:00 would confirm which of the four is dominant — and are worth having on file regardless of which option is chosen.
Replacing the SATA drive is not worth doing The Iware F1 platform runs on SATA lanes, so there is likely no M.2 NVMe slot to upgrade into — a new drive would still be SATA. On top of that, the unit is being demoted to a plain cashier terminal, where a SATA drive is perfectly adequate. Opening an all-in-one till risks the warranty for no real gain. Put the NVMe requirement on the new server instead.
One free thing worth trying while the quotation is pending Move the main cashier lane onto the extra POS terminal and let the Iware F1 run as server only. That removes the heaviest local job — a full Chrome POS window — from the machine everyone depends on. It costs nothing, it can be reversed in minutes, and if posting improves noticeably it confirms the diagnosis before any money is spent.
04

Failure risk

Performance is the visible problem. The structural one is that a single till on an open counter can stop every section at once.

If the main till goes down, everything goes down A hang, a power trip, a spilt drink or a failed fan on that one machine takes all 14 tablets and the extra POS with it. There is no second host to fall back to.
Exposure Today After splitting the roles
Main till fails Every section stops One lane down
Physical environment Open counter AV Room, air-conditioned
Power interruption No UPS on the host UPS-backed, clean shutdown
Hardware service Supplier warranty, carry-in 3-year onsite
Spare capacity None Iware F1 becomes the fallback
The old unit keeps earning Once the server role moves off it, the Iware F1 goes back to being what it was built for — a cashier terminal. Nothing is written off, and its workload drops to a level it can actually handle.
